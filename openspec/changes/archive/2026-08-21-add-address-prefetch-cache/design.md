## Context

現在、店舗の住所は `ShopDetailFetcher.getAddress(shopId)` が「カード popover を開いた」「店舗ページのパネルがマウントされた」タイミングでのみ `/shopDetail/{shopId}` から取得し、`Store`（メモリ上の `this.state` + `GM_setValue` による永続化）にキャッシュする、完全にオンデマンドな仕組みになっている（`src/managers/ShopDetailFetcher.ts`, `src/store.ts`）。店舗名は `CardOverlayManager.decorateCard` が一覧カードの DOM から都度抽出するだけで、どこにも永続化されない（`src/adapters/ListingAdapter.ts` の `extractShopName`）。

issue #26 は「店舗一覧カードに住所を常時表示したい」「同一住所の他店舗をホバーで一覧表示したい」という要望で、後者は特に「一つの場所がいくつもの店舗を出店しているケース（ダークキッチン／バーチャルレストラン）を見つけたい」という動機に基づく。この2つのUI機能に先立ち、まず「一覧を見ているだけで住所と店名が穏やかに集まってくる」データ基盤を作るのが本changeのスコープ。

exploreモードでの対話で、以下の方針に合意している:
- 先読みのトリガーは「カード検出時に全件キューイング」というシンプルな案（IntersectionObserverのようなビューポート監視は行わない）
- 同時実行数の上限とインターバルの両方で出前館サイトへの負荷を抑える
- 店舗名は「既にキャッシュ済みなら信用してスキップ」
- 住所の正規化は「NFKC正規化＋空白整形」程度の軽量な処理から始め、番地抽出や建物名分離のような精緻な処理は将来の課題として残す
- `Store` の `GM_setValue` 書き込みは、短時間の連続更新をまとめて書けるよう debounce する

## Goals / Non-Goals

**Goals:**
- 一覧ページを表示しているだけで、表示された店舗の住所・店名が出前館サイトに負荷をかけない範囲で自動的に取得・キャッシュされる
- 取得した住所を正規化し、同一（とみなせる）住所の shopId をまとめて引けるようにする
- ローカルストレージ（`GM_setValue`）への書き込み回数を、先読みによる連続更新時にも抑える
- 既存のオンデマンド取得（popover/パネルを開いた時の即時取得、手動再取得）の挙動・レイテンシは変えない

**Non-Goals:**
- 店舗カードへの住所常時表示UI、表示トグルのON/OFF UI自体（別change）
- 同一住所の他店舗をホバーで一覧表示するUI自体（別change）
- 番地抽出・建物名分離など、精度の高い住所正規化（将来の改善課題として残す）
- IntersectionObserverなどによるビューポート駆動の先読み（将来、必要になれば検討）

## Decisions

### 1. 先読みキューは新規クラス `PrefetchQueue` として独立させる

`ShopDetailFetcher` は「1件のアドレスを解決する」責務のまま変えず、「いつ・どの順で・どれだけ穏やかに解決を依頼するか」というスケジューリングの責務を新規クラスに分離する。`CardOverlayManager.decorateCard` はカードを見つけるたびに `PrefetchQueue.enqueue(shopId)` を呼ぶだけにする。

- キューは重複投入を無視する（同一 shopId が既にキュー内、または処理中なら無視）。
- `Store.getShopRecord(shopId)?.address` が既にある shopId は投入時点で弾く。
- ワーカーは「同時実行数の上限まで並列にジョブを取り出し、1ジョブ完了するたびに一定インターバルを空けてから次を取り出す」ループとする。
  - 同時実行数の上限: **2**
  - ジョブ完了後、次のジョブを取り出すまでのインターバル: **400ms**
  - （どちらもたたき台の初期値。運用しながら調整可能なようコード上は定数として1箇所にまとめる）

代替案として検討したが採らなかったもの:
- IntersectionObserverでビューポート近傍のみ取得: 見えている分だけ通信するため理想的だが、既存の `MutationObserver`（load-more検知）と役割が重なり実装が複雑になる。今回は「案A: 全件キューイング＋並列数・間隔の制御」で十分に穏やかにできると判断し、シンプルさを優先した。

### 2. 先読みは `Store` が持つ「先読み有効フラグ」に連動して起動/停止する

住所表示トグルのUI自体は別change（issue #26 のUI部分）で作られるため、本changeではそれに先立って `Store` に **先読み有効フラグ**（`STORAGE_KEYS.ADDRESS_PREFETCH_ENABLED`、デフォルト値 `true`）を新設し、`PrefetchQueue` はこのフラグを `Store.subscribe` で監視して OFF→ON の遷移でワーカーを起動、ON→OFF の遷移でワーカーを一時停止する。

- デフォルトを `true` にすることで、住所表示トグルUIがまだ存在しない現時点でも先読み・キャッシュ蓄積自体は独立して動作し検証できる。UIが実装されるchangeでは、このフラグをトグルのON/OFFに直結させるだけでよい。
- 停止してもキューの中身（未処理の shopId 一覧）は破棄しない。次に ON になったときに続きから処理を再開する。
- カード検出によるキューへの投入自体（`enqueue`）は、フラグの ON/OFF に関わらず常に行う。それによって「ONにした瞬間、その時点までに検出済みの全カードから先読みが始まる」という探索時の合意が実現できる。

### 3. 店舗名は `ShopRecord.name` としてキャッシュし、"既にあれば上書きしない"

```ts
export interface ShopRecord {
  name?: string;          // 追加
  address?: string;
  addressFetchedAt?: number;
  judgment?: Judgment;
  judgedAt?: number;
}
```

`CardOverlayManager.decorateCard` で shopId を確定させた直後、`adapter.extractShopName(card)` の結果を使って `Store.getShopRecord(shopId)?.name` をチェックし、未設定のときだけ `Store.updateShopRecord(shopId, { name })` を呼ぶ。店名の取得はDOM抽出のみで通信を伴わないため、`PrefetchQueue` の並列数・インターバル制御の対象外（都度その場で完結する）。

「既にあれば上書きしない」ため、稀に出前館側で店名表記が変わった場合は反映されなくなるが、店名は住所ほど検出の核心ではなく、実害は小さいと判断した（将来必要になれば、住所の手動再取得ボタンと同様に店名の再取得手段を別途足せる）。

### 4. 住所正規化は `normalizeAddress` として `src/logic.ts` に追加する軽量関数

```
normalizeAddress(raw: string): string
  1. raw.normalize('NFKC')   // 全角英数字・記号を半角化
  2. 前後の空白を trim
  3. 連続する空白（全角スペース含む）を1つの半角スペースに圧縮
```

番地だけを抜き出す・建物名を分離するといった処理は行わない。**取得した住所文字列全体を正規化した結果をそのままグルーピングキーにする。** ダークキッチン検出という目的に対しては、出前館の住所表記が番地までしか含まない（テスト `src/logic.test.ts` のサンプル `北海道札幌市豊平区中の島1条5丁目4番1号` など）場合、この軽量な正規化だけでも「同じ番地」の店舗を素直に拾えると見込んでいる。精度が不十分と分かった時点で、正規化ロジックだけを差し替えられるよう関数を1箇所に閉じ込めておく。

### 5. 住所→shopId のグルーピングは都度導出する（専用インデックスは持たない）

`Store` に `getShopIdsByNormalizedAddress(normalizedAddress: string): ShopId[]` のようなメソッドを追加するが、内部実装は `Object.entries(this.state.shopRecords)` を都度フィルタするだけの単純な実装にする。ユーザースクリプトがローカルに保持する店舗数は数百件規模を想定しており、都度の線形走査で性能上の問題は出ないと判断。専用の逆引きインデックスを別途保持して更新のたびに同期する複雑さは避ける。

### 6. `Store` の永続化を debounce する

`Store._setShopRecords`（および同様に `GM_setValue` を呼ぶ箇所）を、呼び出しごとに即時書き込むのではなく、次の形に変える。

- `this.state` は呼び出しのたびに**即時**更新する（メモリ上の読み取りは常に最新）。
- `GM_setValue(STORAGE_KEYS.SHOP_RECORDS, ...)` の実際の呼び出しは `setTimeout` ベースで **800ms** debounce する（呼び出しが連続するたびにタイマーをリセットし、800ms 何も呼ばれなければ1回だけ書き込む）。
- ページ離脱時に直近の変更が失われないよう、`beforeunload` / `pagehide` イベントで保留中の書き込みを強制的に flush する。

既存の `updateShopRecord` 等、呼び出し側のAPIシグネチャは変更しない。

## Risks / Trade-offs

- **[Risk]** debounce中にタブが閉じられると、`beforeunload`/`pagehide` が確実に発火しないブラウザ/状況（例: モバイルでのアプリ強制終了）では直近の更新が失われる可能性がある。 → **Mitigation**: 失われても次回そのカードが表示された時点で再取得されるだけであり、致命的なデータ損失ではない（キャッシュの再構築コストのみ）。
- **[Risk]** 一覧に大量のカード（load-more含め100件超など）が表示されるページでは、先読みキューの消化に時間がかかり、ユーザーが離脱するまでに全件終わらない。 → **Mitigation**: 今回は許容する。取得済み分は永続化されるため、再訪時にはキャッシュが積み上がっていく。将来的に「見えている分だけ優先」する改善は別途検討できるよう `PrefetchQueue` をキュー投入とワーカーで分離した設計にしてある。
- **[Risk]** 同時実行数・インターバルを絞っても、出前館サーバー側のレート制限やbot対策に引っかかる可能性はゼロではない。 → **Mitigation**: 個々の fetch 失敗は既存の `AddressResult: { status: 'error' }` にフォールバックし、キュー全体は止めず次の shopId の処理へ進む。ユーザーが必要なら popover の手動再取得で個別にリトライできる。
- **[Risk]** 軽量な正規化（NFKC＋空白整形のみ）では、番地表記のゆれ（"1-2-3" と "1丁目2番3号" など異なる書式）や、実際には建物名・部屋番号が含まれるケースを吸収しきれず、同一住所の店舗を取りこぼす／過剰にまとめてしまう可能性がある。 → **Mitigation**: 初期実装として許容し、実運用で精度不足が判明した時点で `normalizeAddress` のロジックだけを個別に強化する（呼び出し側への影響を閉じ込めてある）。
- **[Trade-off]** 住所→shopIdの逆引きを都度の線形走査で行うため、キャッシュされた店舗数が将来大きく増えた場合はコストが線形に増える。専用インデックスを持たない代わりに実装・同期の複雑さを避けている。

## Migration Plan

- データマイグレーションは不要。既存の `GM_setValue` に保存済みの `ShopRecords` には `name` フィールドが存在しないが、`ShopRecord.name` はオプショナルなので `undefined` として自然に扱われ、初回カード検出時に埋まっていく。
- ロールバックは通常のコード変更のロールバックと同様（永続化データのスキーマは後方互換）。

## Open Questions

- 同時実行数（2）・インターバル（400ms）・debounce時間（800ms）の具体値は実運用で体感しながら調整が必要になる可能性がある。初期値として妥当だが、tasks側で「調整しやすいよう定数を1箇所にまとめる」ことを明記する。
- 別changeで住所表示トグルUIが実装される際、本changeで新設する `ADDRESS_PREFETCH_ENABLED` フラグをそのまま流用するか、UI側で新しいキーを持たせて同期するかは実装時に判断する。
